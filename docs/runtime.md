# Runtime, memory and integrations

## Conversation and workers

There is one permanent main conversation. Workspaces supply execution directories and instructions for workers and scheduled work; they are not separate user chats.

Pi Durable persists the main conversation, linear workers, queued input and report delivery in SQLite. All subagents run asynchronously, including nested helpers started by workers or cron. `run`, `queue` and `resume` return a Session ID without waiting for completion, keeping the caller available for steering. Start helpers with `run`, then join results explicitly with `await`; start multiple helpers before awaiting to run them in parallel. `steer` and `stop` manage running work. Reports return to the spawning parent. In main, `await` yields the turn for later result delivery; in a worker or cron turn, it joins a direct child and returns its final result without a duplicate report. Other helper reports wait until joined or the parent turn finishes.

`run` creates a new session and rejects `sessionId`. Use `queue` for a running session or `resume` for a finished one; `await`, `queue`, `resume`, `steer` and `stop` require `sessionId`. `queue`, `resume`, `steer` and `stop` follow the same workspace scope as discovery; worker `await` retains its direct-child rule. All project workers, including cron roots and descendants, delegate only within their current workspace; main and assistant-workspace workers may delegate across workspaces. Cron runs and queues remain distinct, with explicit interaction between agents. These are coordination guardrails against accidental interference, not a security boundary: agents have shell access as root.

A subagent can call `subagent({action: "report", prompt: "…"})` to send an explicit intermediate report to its actual spawning parent and continue working. No `sessionId` is accepted; main and cron workers cannot use this action. The report snapshots the current assignment’s attached file/diff/site/browser artifacts with stable refs; the parent forwards selected artifacts with `attach_artifacts`. Ordinary commentary stays local. Each tool invocation has a durable request ID, so replay does not duplicate delivery. Reports do not complete the assignment or satisfy `await`; final reporting and joins remain separate. A busy parent receives the update as steering, including while waiting for a child.

`subagent({action: "list", limit: 50, cursor: "…"})` discovers registered subagents, including archived ones. Each page scans at most 1–100 conversations (default 50), returning stable string `sessionId`, workspace, status and assignment start time. Pass `nextCursor` back unchanged until absent; filtered pages can be empty. Prompts and transcripts are excluded. Main and assigned workers in the configured assistant workspace see the orchestration's workers across all workspaces; other workers see only peers in their own workspace. Ordinary subagents, cron roots and cron descendants share this policy. This uses the reader's current workspace, not the target's or parent's: nested workers qualify only while they themselves belong to the assistant workspace. A workspace-changing resume grants or removes that access; without a configured assistant workspace, workers remain same-workspace only. The same scope permits explicit management through `queue`, `resume`, `steer` and `stop`; inspection includes explicit report/result text and artifact forwarding, not transcripts. Cron ancestry and job/run identity do not restrict coordination. Unknown and inaccessible inspect targets share one error. Discovery does not grant access to unrelated or unregistered conversations.

`subagent({action: "inspect", sessionId: "…"})` reads status without waiting, joining or acknowledging delivery. `latest` contains the newest explicit report or completed result, its assignment ID and up to 16,000 text characters (`truncated` indicates clipping). A previous assignment's result remains available during resumed work until a newer report arrives; changing workspace clears prior report/result pointers so another workspace cannot inspect earlier output. Immutable artifact descriptors and forwarding refs remain complete; `attach_artifacts` can reuse them directly. No commentary, tool transcript or credential fields are read. Explicit report/result prose is agent-authored, not a secret-redaction service. Historical completed assignments remain inspectable; progress snapshots are retained for reports made with this implementation. Existing mutation/join rules are unchanged: `await` in workers still requires a direct child, while `steer` can target a known running sibling.

Cron jobs have explicit titles. `cron({action: "list"})` returns compact summaries without prompts; `cron({action: "get", jobId: "…"})` returns a single full job. `add` requires a nonempty `title`; `update` can rename it without changing execution settings.

A job can have one `at`, `every` or `cron` schedule, or `schedule: {kind: "multiple", triggers: [...]}` containing several of those triggers. They share one job ID, prompt and execution/delivery settings. Each trigger has its own durable deadline; the earliest is the job’s `nextAt`. All triggers due at admission coalesce into one run, including overdue occurrences after downtime. Intervals retain their independent cadence, and consumed one-shots stay consumed across restarts. Replacing `schedule` resets its deadlines. An exhausted job is disabled; an all-one-shot job is retired after its final successful run, while failures remain available for inspection. Existing single-trigger jobs and archived runs retain their format.

Due cron jobs wait for network connectivity before admission, retaining their persisted deadlines. Connectivity is checked again after 30 seconds; missed triggers coalesce as after process downtime. A transport failure during an active model request waits and retries that same durable request while independent connectivity checks confirm the host is offline. Offline attempts do not append model errors to conversation history. Pending requests survive process restart and can be stopped normally. HTTP, authentication, TLS and configuration errors remain visible; transport errors while connectivity is available retain the provider's normal error/retry behavior. Connectivity checks use HTTPS to Google and Cloudflare plus TCP to `1.1.1.1:443`; any response/connection proves connectivity.

Each cron run starts a fresh worker in the selected workspace. Workers in the assistant workspace receive main OptChat memory and navigation tools. Delivery can go through the assistant or directly to the user. Helpers stay with their cron parent; only the completed cron turn's final output is delivered onward.

Outgoing prompts appear immediately, including attachment names, and survive refresh until the server publishes the matching message. Failed submissions restore the draft; cancelling queued input removes its outgoing entry.

## Memory

Main combines an OptChat summary prefix with an ordinary session tail reconstructed from durable originals. The tail retains user and assistant messages, subagent/runtime reports, tool calls and results, reasoning signatures and images. Effective system instructions lead the request; historical system patches remain in the archive. There is one size policy: 200,000 UTF-8 bytes of serialized message JSON (`SESSION_TAIL_BYTES`), with a 20% rollover batch. Above this threshold, background compression archives the oldest complete runs, targeting 80% remaining. Run boundaries keep tool calls/results together. The threshold is soft: an active run or slow compression can temporarily exceed it. Normal admission does not wait for model inference. Pi's estimator enforces the selected model's actual context window and answer reserve. Only at that hard limit does admission await in-flight archival and adopt its prepared prefix for the same submission; an oversized active run fails explicitly without dropping originals.

The stable prefix and tail boundary advance atomically only after the entire replacement prefix is prepared. Until publication, requests retain the old prefix and full original tail. Completed nodes survive restart; interrupted work resumes on the next request. Existing prepared trees can seed the initial boundary without inference. OptChat has no separate uncompressed projection trail in model requests. The view-size target controls summary rendering, not session-tail retention. Originals remain permanently archived. `memory_zoom` expands child summaries with UTC timestamp ranges or retrieves an original timestamp, non-thought text and images at leaf zoom (`n=1`); `memory_search` uses FTS5 to search original text by 1–12 conjunctive words, ranked exact-first then by BM25 relevance. Longer alphabetic words also match conservative whole-word prefix variants in either direction (minimum five characters, at most three additional characters and 70% shared length); short words and identifiers stay exact. Tool calls and results are excluded from search unless requested. Full metadata, images and reasoning remain in the permanent archive; reasoning is excluded from compression.

For main user inputs, automatic recall searches current words (up to 24) separately from recent conversational context (up to eight), without model calls. Corpus rarity weights terms without a minimum rarity threshold. OR/BM25 retrieves up to 100 current-topic candidates and 40 context candidates; independent current-term queries contribute up to eight hits each. Candidate originals are reranked by weighted query-word coverage, with up to six current-topic excerpts and two context excerpts. Each excerpt keeps its zoomable OptChat ID; neighbors are not automatically included. Use `memory_zoom(id - 1, 1)` or `memory_zoom(id + 1, 1)` to retrieve neighboring originals across summary boundaries when needed; a neighbor can be a tool call or runtime note. Visible leaves, the latest 16 leaves and duplicate excerpts are excluded. The bounded recall block sits immediately before its user input, after the stable overview; it is pinned per input across tools and restarts. Recall only uses spare admission space and cannot repin the overview. Under budget pressure it loses complete excerpt lines before any original message. Runtime reports and workers do not trigger automatic recall. Lexical heuristics do not understand irregular word forms, semantic relevance or whether historical advice remains current.

Packets persist the exact view, input boundary, generation and covered message counts for retry and restart. The view and session-tail boundary stay pinned through tool rounds, including when background archival publishes a replacement, unless the actual model capacity requires adopting a completed archive. The input boundary and active messages, including reasoning signatures and tool results, remain unchanged. Later runs adopt completed rollovers. No message-count limit or overlap-deduplication pass is used; the archive boundary separates originals from summaries. Compression runs on a separate writer queue; complete prefixes publish through short, atomic generation/checkpoint-checked commits. Repairs publish child generations with unchanged nodes inherited from the previous prefix, so pinned zooms retain their tree. Completed nodes and checkpoints survive restart; an interrupted inference without a committed node may repeat.

Fresh workers targeting the assistant workspace pin the main archive prefix, its generation and the native main session tail on their first model request for their lifetime. This is injected memory context, not a copied worker transcript. Main subagent reports and recent tool results remain available before rollover. Workers in other workspaces receive no main-memory overview or navigation tools. Pi Durable compacts worker context while retaining original history. Main declines native compaction.

Settings → Memory controls the summarization model and free-text language. The defaults are `openai-codex/gpt-6-luna` and English. `BATTY_MEMORY_REASONING` controls reasoning; `BATTY_MEMORY_MODEL` is not used. Changing language does not rewrite existing summaries or original messages. `scripts/prepare-memory.ts` prepares memory without starting HTTP.

### Usage accounting

OptChat requests lead with effective instructions and tool declarations. Authenticated `GET /api/memory/usage` separates incremental and rebuild totals: attempts, measured/unmeasured outcomes, uncached input, cache reads/writes, output, reasoning and API-equivalent catalog cost. Reasoning is included in output, not added to it. This measures returned API usage, not subscription spending. Coverage starts with instrumentation; historical compression costs and provider-internal retries without returned usage are not recorded.

The durable `batty.memory-usage` document stores totals. `batty.memory-call` entries in `runtime.sqlite` hold per-attempt operation, generation/node range, source hash, model, timing, stop reason, response ID and returned usage. They contain no source text or provider error messages and do not enter the memory tree or conversational usage totals.

## MCP and codemode

MCP uses one `.batty/mcp.json` configuration and a shared connection registry across workspaces. Stdio servers run from the configured data root; use absolute paths for workspace resources. MCP tools are discovered and called through codemode, which runs JavaScript in a QuickJS sandbox and can compose ordinary tools as well.

Settings use `/api/settings/mcp`; connection status and actions use `/api/mcp`. Workspace-specific MCP configuration, overrides and scoped API parameters are not supported.

## Browser lifecycle

Each workspace shares one Chromium instance, profile, logins and tabs between main and its workers. Other workspaces have separate browsers. Agents can list tabs and address a specific `pageId` to coordinate; the active page is also shared. Browser actions are serialized per workspace.

Detached browser instances and tabs survive Batty restarts and expire after **60 minutes without browser activity**. Active and queued browser calls are protected during cleanup. Expiry runs at startup and each minute without resetting the persisted inactivity clock. Stopping a worker does not close the shared browser. Explicit browser close invalidates its attachments for everyone using it. Close and inactivity stop Chromium and its display, discard live tab/frame registries and viewer handles, and retain the workspace's disk profile (including persistent cookies, logins and site storage). Neither logs out or clears browsing data. After close or expiry, `browser open` starts a new instance with that same profile, including across Batty restarts; live JavaScript state is not preserved. Existing isolated profiles are reused in place.

### Shared cloud browser

`browser({action: "open", url: "https://example.com", cloud: true})` enables interactive VPS access and attaches a private live-browser button; `browser({action: "attach"})` attaches that same browser again. It opens a popover, not a local browser session or a copy of cookies. Agent and human share the same Chromium pages, login and live state. Ordinary tool calls have no shared viewer by default. On Linux their persistent Chromium process uses a private authenticated X display so a viewer can attach to the same process later. Before viewing, a new cloud browser uses a 390 × 640 viewport unless specified. The viewer matches its available area in CSS pixels and requests the display’s pixel density, up to 3×. Touch/mobile viewers use mobile Chromium device metrics, screen size, touch support, user-agent and client hints; desktop viewers use desktop emulation. Rotation/resizing keeps the page alive. Switching between mobile and desktop reloads the existing page for server-selected layouts while preserving cookies, storage and login. Opening the phone keyboard keeps the remote layout stable.

The popover shows one page with its address in the header; bare domains use HTTPS and focusing the address selects the full URL. Popups become the visible page, and Back returns to the opener when the popup has no history. Agent tab/drag/key controls remain available through the browser tool. Touch swipes and mouse wheels scroll the remote element under the pointer, including nested containers. Focusing an editable field reveals a local keyboard editor; changes replace the remote value, and Enter submits single-line fields. Native H.264 capture targets 30 frames/s, bounded by transport and presentation credits. Scrolling uses up to 2× density; capture returns to requested density after 150 ms wheel idle or one second after touch release to cover momentum. Viewing counts as browser activity. Closing/backgrounding the viewer disconnects streaming without closing Chromium. Transport interruptions and transient navigation/capture errors reconnect automatically with backoff, capped at 15 seconds. Expired/closed browsers remain closed; other permanent errors offer manual retry without creating a new browser. `action: "close"` or idle expiry permanently invalidates its handles. Attachments survive service restarts and can be explicitly forwarded with their `browser:` artifact refs. Forwarding preserves the same live session and expiry; it does not publish access or open another browser. See [response artifacts](artifacts.md).

FFmpeg captures the private X display and encodes H.264, delivered through Batty's authenticated binary WebSocket. WebCodecs decodes into the viewer canvas. Each viewer has at most four unacknowledged frames and a bounded GOP-aware queue; overflow discards the dependent frames and waits for a periodic keyframe. There is no JPEG fallback. Native capture requires Linux, Xvfb, xauth and FFmpeg with x11grab/libx264. Viewports support at most 1365 CSS pixels per dimension. Existing headless browser processes retain their login and tabs but cannot be viewed through this transport; replacing one requires an explicit close/open. Scroll input uses the same socket, with an ordering fence before HTTP controls such as clicks. Controls are same-origin, allowlisted HTTP commands serialized with agent actions; busy operations and stale-view input are rejected. No desktop, extra public port, iframe capability link or public-sharing option is exposed. Local iPhone passkeys, clipboard and file pickers are not forwarded.

## Offline reading

The main thread opens from an authentication-scoped IndexedDB cache before network requests. It fills at least the latest 24 hours, retaining up to seven days within a 32 MiB soft budget, and reports an error rather than exceeding 128 MiB or dropping the latest day. Quota failures preserve the previous complete cache. Logout invalidates cached reading across tabs. Worker sessions are excluded, but their main-thread notices remain.

Reconnect uses the last durable message ID and an inclusive overlap record, updating existing IDs and live state without resending the entire conversation. Older history loads in pages. Sending requires a live connection; offline drafts are not queued for delivery.

Images use lazy 768-pixel WebP previews with links to originals. The service worker stores up to 128 private previews per authentication scope. Historical rows are virtualized; eight tail rows stay mounted. See [operations](operations.md#checks) for the production offline check.
